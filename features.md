# DevToolz — идеи и план

Живой документ для набросков, пока пакет не оформился. Не финальная
спецификация — фиксируем идеи по мере обсуждения, приоритизируем и режем
по ходу дела.

## Концепция

Набор небольших, самодостаточных CLI-команд, автоматизирующих рутинные
задачи разработчика. Один и тот же подход, что уже отработан в
`strip-comments` (`C:\work\Наработки\strip-comments`) — там, где нужен
реальный AST-анализ, а не наивный regex/построчный скан. Каждая команда
решает ровно одну конкретную раздражающую задачу, не пытается быть
универсальным фреймворком.

Не дублируем то, что уже покрыто другими пакетами:

- **lintsync** — синхронизация конфигов линтеров/форматтеров между
  проектами.
- **polyrepo-cli** — версии, PR, публикация, cross-package dependency
  drift между локальными репозиториями.

## Решено

- **Название пакета**: `devtoolz` — свободно на npm (проверено
  `registry.npmjs.org`, 404 на `devtoolz` и `dev-toolz`).
- **Архитектура**: единый CLI-раннер с подкомандами, на `commander` —
  как у `lintsync`/`polyrepo-cli`.
- **MVP — 4 команды**: `strip-comments`, `console-strip`, `dead-exports`,
  `case-check` — ✅ все реализованы, протестированы (87 юнит-тестов) и
  прогнаны вживую и на собственных исходниках `devtoolz`, и на реальном
  pnpm-workspace `inview`.

## Тон вывода

Не сухой/безликий, но и не надоедливый — юмор дозированно, по делу, не на
каждой строке.

- **Где уместно**: разовые моменты — приветственный баннер при запуске
  (компактный, не на весь экран), итоговая фраза, когда всё чисто (0
  находок) — вот тут можно и с ASCII-рисунком, и с шуткой. Это момент
  праздника, не мешает разбору проблем.
- **Где НЕ уместно**: сами результаты — список file:line, находки,
  ошибки — остаются сухими и легко сканируемыми, без шуток внутри
  таблицы/списка. Когда находок много (реальная проблема) — тон
  сдержанный, без «пошутить над багом». Переусердствовать с весельем в
  момент, когда у человека 40 проблем в отчёте — тонально мимо.
- **Технический гейт**: юмор/ASCII/цвет автоматически выключаются в
  неинтерактивном/CI-окружении (`!process.stdout.isTTY`,
  `process.env.CI`, `NO_COLOR`) — как в остальных инструментах экосистемы
  так и должно быть, эти CLI гоняют и в pipeline, не только руками. Плюс
  явный `--quiet`/`--plain` флаг.
- **Реализация**: не хардкодить шутки по месту в каждой команде — общий
  пул фраз (например `src/format/vibes.ts`), ротация случайной фразы из
  набора на каждый повод (чисто / первый запуск / и т.п.), чтобы вывод не
  приедался и легко было подкрутить тон в одном месте.

## MVP-команды — контракты

### Общие флаги (все команды)

По образцу `lintsync`:

| Флаг              | Смысл                                                                                           |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| `--cwd <path>`    | корень, от которого считаются относительные пути (default: `process.cwd()`)                     |
| `--json`          | машиночитаемый вывод, отключает и юмор, и человеческий отчёт                                    |
| `--quiet`         | подавить вывод при чистом результате                                                            |
| `--verbose`       | развёрнутые детали по каждой находке                                                            |
| `--ignore <glob>` | доп. игнор поверх дефолтных (`node_modules`, `dist`, `build`, `.git`, `coverage`) — повторяемый |
| `--ext <list>`    | через запятую, какие расширения трогать (default: `.ts,.tsx,.js,.jsx,.cjs,.mjs,.vue`)           |

Для команд, которые **пишут в файлы** (`strip-comments`, `console-strip`,
`case-check --fix`) — ещё и:

| Флаг        | Смысл                                                                                                      |
| ----------- | ---------------------------------------------------------------------------------------------------------- |
| `--dry-run` | только показать, что изменилось бы, ничего не писать                                                       |
| `-y, --yes` | применить изменения (без этого — по умолчанию превью/интерактивное подтверждение, ничего не пишется молча) |
| `--diff`    | unified diff по каждому затронутому файлу, а не только список имён                                         |

Exit code везде: `0` — чисто/применено без проблем; `1` — есть находки (в
режиме проверки/`--dry-run`) или необработанные edge-кейсы, требующие
ручного разбора — важно для CI-гейтов.

### `strip-comments` — ✅ реализовано

Портировано из черновика (`C:\work\Наработки\strip-comments`) в
`src/commands/strip-comments/`, с обоими улучшениями из контракта
(`--keep-jsdoc`, `--respect-gitignore` вместо хардкода `SKIP_DIRS`) и
27 юнит-тестами (`src/tests/`). По пути нашлись и исправлены 2 реальных
бага (в т.ч. один унаследованный от самого черновика):

- Строчный `<!-- -->` в `<template>`, стоящий ПОСЛЕ реального контента на
  той же строке (`<div>x</div> <!-- gone -->`), ошибочно распознавался как
  «комментарий на всю строку» и съедал перенос строки, склеивая соседние
  строки — regex-эвристика черновика проверяла только сам матч в отрыве от
  контекста строки. Исправлено: `<template>`-блок теперь использует тот же
  построчный алгоритм (проверка по границам РЕАЛЬНОЙ строки), что и
  TS-часть, через общий `apply-deletions.ts`.
- CRLF-файлы — схлопывание 3+ пустых строк оставляло висячие `\r`.
  Исправлено с сохранением исходного стиля переноса строк.
- (Не баг черновика, а моя собственная ошибка на этапе портирования)
  `moduleResolution: NodeNext` ломает default-импорт пакета `ignore`
  (CJS без `exports`-поля) — обошлось через `createRequire`.
- `walk()` падал необработанным исключением при пути вне `--cwd` —
  найдено smoke-тестом, исправлено.

**Как работает** (из черновика, сохраняем): полный TS-парс файла →
находит все string/template/regex/JSX-text спаны → маскирует их
содержимое (та же длина, позиции не сдвигаются) → сканирует
замаскированную копию на реальные комментарии → удаляет ровно эти байтовые
диапазоны из ОРИГИНАЛЬНОГО текста. Ничего не форматируется заново — код
вне комментариев побайтово идентичен. `.vue`-файлы: `<script>`-блок через
тот же TS-парсер, `<template>`-блок — `<!-- -->` через regex (уже так
работает, не более «умный» Vue SFC-парсер — см. edge-кейс ниже).

**Специфичные флаги**:

- `--keep-jsdoc` — не трогать `/** ... */` прямо над `export`-объявлением
  (черновик стрипает вообще всё; это улучшение, которого в нём пока нет —
  экспортируемые типы/пропсы теряют IDE-тултипы иначе).
- `--respect-gitignore` (default `true`) — не трогать файлы, игнорируемые
  git (черновик просто хардкодит `SKIP_DIRS` под конкретный проект —
  в реальном CLI так не годится, разные репо по-разному устроены).

**Edge-кейсы**:

- Пустой `catch {}`, у которого был только комментарий внутри — после
  удаления может словить ESLint `no-empty` (правило считает комментарий
  «непустым телом»). Инструмент это не чинит сам, только предупреждает в
  отчёте — исправление (`return`/реальный стейтмент) за разработчиком.
- `.d.ts`-файлы — по умолчанию НЕ входят в `--ext`, трогать только явно.
- Shebang (`#!/usr/bin/env node`) в начале CLI-файлов — не должен
  восприниматься как обычный текст и ломаться; проверить отдельно.
- CRLF (Windows) — черновик схлопывает `\n{3,}` → `\n\n`, но при CRLF
  между `\n`-ами остаются `\r` — нужно `\r?\n(\r?\n){2,}` или
  нормализация окончаний строк, иначе после стрипа расползаются лишние
  `\r`.
- `.vue` без `<script>` или без `<template>` — просто ничего не делает с
  отсутствующим блоком, ок.
- Комментарий внутри `<template>`, который на самом деле часть строки в
  атрибуте (`:title="'<!-- not a comment -->'"`) — regex-подход для
  `<template>`-блока (в отличие от TS-парсера для `<script>`) этого не
  отличит и может испортить строку. Известное ограничение черновика,
  документируем как есть, не обещаем 100% для `<template>`.

### `console-strip` — ✅ реализовано

Тот же AST-подход, что в `strip-comments`, но ищет не комментарии, а
`console.*`-вызовы и `debugger;`, которые являются **целым стейтментом**
(а не частью большего выражения). Переиспользует `apply-deletions.ts`/
`walk`/`diff`/`vibes` из инфраструктуры `strip-comments` без изменений.
45/45 тестов (15 новых юнит + 3 на `.vue`), typecheck/lint/prettier чисто,
живой smoke-тест через `node dist/cli.js console-strip` подтвердил все
edge-кейсы разом на одном файле: строка `'console.log(...)'` не тронута,
многострочный вызов удалён целиком, `console.warn` оставлен (не в
дефолте), `console.log(x) || 42` и `if (x) console.log(...)` без скобок —
оба НЕ удалены и репортятся с точными `file:line:column`.

**Специфичные флаги**:

- `--methods <list>` — какие методы `console` трогать (default:
  `log,debug`; `warn`/`error` сознательно НЕ в дефолте — это часто
  легитимное production-логирование, не мусор).
- `--no-debugger` — не трогать `debugger;` отдельно от `console.*`.

**Edge-кейсы**:

- `console.log(x)` как часть большего выражения (`const r = console.log(x) || y`)
  — не удаляется молча (это не отдельный стейтмент), попадает в отчёт как
  «оставлено, требует ручного разбора».
- `if (x) console.log(x);` без фигурных скобок — наивное удаление оставит
  `if (x) ;`. Инструмент такое НЕ трогает автоматически — репортит
  отдельным пунктом («внутри однострочного тела без скобок»), решение за
  разработчиком (обернуть в `{}` или удалить целиком вручную).
- Многострочные вызовы (`console.log(\n  a,\n  b\n)`) — нужен точный
  спан всего стейтмента, не только первой строки.
- `.vue` — тот же script-block-экстракшн, что в `strip-comments`.

### `dead-exports` — ✅ реализовано

Ищет именованные экспорты, на которые нигде в дереве нет импортов.
**Ключевая оговорка**: для опубликованного пакета корневой barrel —
это публичный API, «не используется внутри репо» ≠ «мёртвый код». По
умолчанию экспорты из объявленных публичных точек входа (`exports`/
`main`/`module` в `package.json`) исключены из проверки — иначе
инструмент будет врать про половину любой библиотеки.

**Специфичные флаги**:

- `--entry <path>` — переопределить автоопределённые публичные точки
  входа (повторяемый флаг).
- `--strict` — включить в проверку и публичные точки входа тоже (сигнал
  тогда другой: «на этот символ вообще нет ссылок нигде, кроме самого
  экспорта» — жёстче, но и шумнее для библиотеки; включать осознанно).
- `--workspace` (auto-detect по умолчанию) — если рядом
  `pnpm-workspace.yaml`/`package.json`'s `workspaces`, сканировать
  ссылки по всему workspace, а не только внутри одного пакета (иначе
  `@macrulez/inview-vue`, использующий экспорт из `inview-core`, даст
  ложный «мёртвый экспорт» — ровно структура `inview`).

**Edge-кейсы**:

- Реэкспорты (`export { X } from './y'`) — трассируются через цепочку;
  «мёртвость» проверяется у исходного символа, репорт указывает
  реальный файл-источник, а не только барrel.
- Динамические импорты с вычисляемым путём (`import(pathVar)`) — не
  резолвятся статически, помечается предупреждением «есть динамические
  импорты, возможны ложные срабатывания», не молчаливая дыра.
- `export default` — детект «использования» мягче (любой default-импорт
  модуля засчитывается), не пытаемся доказывать честную мёртвость —
  документируем как best-effort, не такой строгий, как для именованных
  экспортов.
- `export type`/`export interface` — типовые импорты (`import type`)
  тоже считаются использованием.
- Циклы реэкспортов — нужен cycle-detection, чтобы не зависнуть.
- Файлы, импортируемые только ради побочного эффекта в моках
  (`vi.mock('./x')` строкой, не реальный `import`) — не отслеживается,
  known limitation, не пытаемся угадывать содержимое строк.
- **Конфиги инструментов сборки** (`*.config.ts`/`.js`/`.mjs`/`.cjs` —
  `tsup.config.ts`, `vitest.config.ts` и т.п.) исключены из скана по
  умолчанию — их `default`-экспорт грузит сам инструмент (tsup/vitest) по
  имени файла, а не через `import` внутри репо, так что для статического
  анализа он всегда выглядит «мёртвым». Найдено и подтверждено на
  реальном прогоне против `inview` (все `tsup.config.ts`/
  `vitest.config.ts` там ложно светились, пока не добавил игнор).
- **Файлы, на которые ссылаются по строковому пути через API фреймворка**
  (не найдено решения, known limitation) — например, Nuxt-модуль
  (`addPlugin(resolver.resolve('./runtime/plugin.client'))`) резолвит
  путь сам, без единого `import`. Тоже подтверждено на реальном коде
  `inview`'s `packages/nuxt` — единственный оставшийся false positive
  после фикса конфигов.

**Проверено на реальном коде, не только на синтетических тестах**: прогнал
против собственных исходников `devtoolz` (нашёл 7 настоящих мёртвых
экспортов, все подтверждены руками через grep) и против реального
pnpm-workspace `inview` — межпакетное разрешение (`inview-vue` →
`inview-core`) отработало верно без единого ложного срабатывания.

**Реальный баг, найденный 2026-09-25 при подготовке фикстуры для
npm-center-документации (не тестами)**: именованный реэкспорт
(`export { x } from './y'`) помечал публично достижимыми **все**
экспорты файла `./y`, а не только `x` — `markAllReachable()` при обходе
любого реэкспорта (именованного или `*`) одинаково маркировал весь
экспорт-список целевого файла. Для барrel-файла, ре-экспортирующего
только часть символов файла, это молча прятало от отчёта настоящие
мёртвые экспорты, объявленные рядом с легитимно ре-экспортированными —
именно тот класс пакетов, ради которого команда существует. Исправлено —
именованный реэкспорт теперь резолвит происхождение через
`resolveExportOrigin()` и маркирует достижимым только этот конкретный
символ; `*`-реэкспорт по-прежнему маркирует весь файл (корректно, он и
должен). Регрессионный тест добавлен.

### `case-check` — ✅ реализовано

Каждый относительный (и алиасный, если резолвится) `import`/`require`
сверяется с РЕАЛЬНЫМ регистром файла на диске (через `readdir`, не через
файловую систему ОС «как есть» — на Windows/Mac она соврёт).

**Реальный баг, пойманный собственными тестами**: первая версия не
учитывала, что весь код `devtoolz` (как и типичный NodeNext-проект)
пишет `import ... from './core.js'`, хотя реальный файл — `core.ts`.
Проверка расширения «как есть» считала это вообще другим файлом (не
просто другим регистром), и все 6 тестов на таком паттерне падали.
Исправлено — при явном расширении в спецификаторе теперь дополнительно
пробуются NodeNext-эквиваленты (`.js`→`.ts`/`.tsx`, `.mjs`→`.mts`,
`.cjs`→`.cts`), а в исправленном варианте сохраняется ИЗНАЧАЛЬНО
написанное расширение — меняется только регистр базового имени.

**Проверено на реальном коде**: 0 находок и на `devtoolz`, и на `inview`
(оба пишут регистр корректно — ожидаемо). Отдельно прогнал живой
сквозной сценарий через собранный CLI (не юнит-тест) — `--fix --diff
--dry-run` показал верный diff, `--fix -y` реально переписал файл на
диске с сохранением стиля кавычек.

**Специфичные флаги**:

- `--fix` — единственная из MVP-команд, где автофикс низкорисковый
  (чистая подмена текста специфайера на реальный регистр, код не
  удаляется) — но всё равно за `-y`, для единообразия с остальными
  командами.
- `--tsconfig <path>` — для резолва алиасов (`@/…`, `~/…`) через
  `compilerOptions.paths`/`baseUrl` (auto-detect `tsconfig.json` в
  `--cwd` по умолчанию).

**Edge-кейсы**:

- Импорт без расширения (`import './Foo'` → реальный `Foo.ts`) —
  сверяется общий префикс без расширения, а не весь путь буквально.
- Каждый сегмент пути проверяется отдельно, не только последний
  (`./Utils/helper` при реальной `utils/` — тоже находка, не только
  финальный файл).
- Импорт директории, резолвящийся в `index.ts` (`import './components'`)
  — проверяется регистр и самой директории, и index-файла.
- Голые импорты пакетов (`import 'lodash'`) — вне scope, не трогаем
  `node_modules`.
- Регистро-нечувствительный git может вообще не записать переименование
  файла как рассинхрон казуса локально — инструмент сверяет с тем, что
  РЕАЛЬНО лежит на диске прямо сейчас, не с git-историей; это
  ограничение метода, не баг.
- Subpath imports (`#internal/...`, `package.json`'s `imports` map) — вне
  scope для MVP, документируем как неподдерживаемое пока.

### `exports-doctor` — ✅ реализовано

Резолвит каждый путь, заявленный в `package.json` (`main`/`module`/
`types`/`typings`/`bin`/`exports`, включая вложенные condition-объекты,
subpaths-карты и fallback-массивы), на реальный файл на диске — тот же
класс проверки, что раньше делали руками при разборе `vue-image-kit`'s
`/cdn`-бага.

**Находки**: `missing` (путь не резолвится вообще), `case-mismatch`
(резолвится, но не тем регистром — показывает реальный путь), `missing-shebang`
(bin-файл без `#!/usr/bin/env node`), `types-missing` (рантайм резолвится
чисто, но ни одно condition-значение под этим subpath'ом вообще не
объявляет `types` — тот самый класс бага, из-за которого TS-потребитель
молча остаётся без типов).

**Реальный баг в собственном дизайне, пойманный тестами (не руками)**:
первая версия `types-missing`-проверки срабатывала на ЛЮБОМ subpath'е без
явного `types`, включая простые строковые `exports["."]` без каких-либо
condition-ключей вовсе — а для такой формы TypeScript и так подхватывает
соседний `.d.ts` по конвенции (сравнение с `main`), так что это была
ложная находка. Исправлено — проверка теперь смотрит только на записи,
реально объявленные ВНУТРИ condition-объекта (`{ import, require, ... }`
без `types`-соседа), различие сохраняется через новое поле
`isConditionEntry` на каждом `DeclaredPath`. Заодно исправлен соседний баг
в том же проходе — `break` после первой находки останавливал вообще весь
цикл по всем subpath'ам, а не только по текущему ключу, из-за чего при
нескольких сломанных subpath'ах репортился только первый; заменено на
`Set` уже отфлагованных ключей.

**Проверено на реальном коде**: 0 находок на всех 21 реальных пакетах в
`C:\work\NPM` (ожидаемо — эти классы багов уже были исправлены руками в
прошлых сессиях, включая тот самый `vue-image-kit`'s `/cdn`) — хорошая
негативная проверка на ложные срабатывания на большой реальной выборке.

**Флаги**: `[dir]` (позиционный, по умолчанию `.`) — путь к директории
пакета (не дереву, читает один `package.json`); только `--json`/
`--quiet`/`--plain` — без `--cwd`/`--ext`/`--ignore`, так как команда не
обходит дерево файлов.

### `readme-check` — ✅ реализовано

Вытаскивает `ts`-блоки (по умолчанию; `tsx`/`js`/`jsx` — через `--lang`)
из README/доков и реально тайпчекает их через TypeScript Compiler API
против собственного `tsconfig.json` пакета — виртуальный файл кладётся
ПРЯМО в корень пакета (рядом с `package.json`), поэтому резолвятся и
относительные импорты, и self-reference импорт по собственному
опубликованному имени пакета (`import { x } from '@scope/pkg'`), если
`moduleResolution` пакета это поддерживает. Только тайпчек, код никогда
не выполняется.

Каждый блок проверяется в изоляции (не накапливается с соседними блоками
в одном файле) — см. ниже, почему это осознанный выбор, а не упрощение.

**Реальный процесс дизайна — 3 итерации дого-дуинга на всех 21 реальных
пакетах в `C:\work\NPM`, каждая вскрыла новый класс ложных срабатываний**:

1. Первая версия: `path.join()` строил путь виртуального файла с
   обратными слэшами на Windows, а TypeScript внутри ВСЕГДА нормализует
   пути к forward-slash — сравнение `fileName === virtualFileName`
   никогда не совпадало, виртуальный файл считался "не найденным", 0
   диагностик вообще ни разу не производилось. Поймано изолированным
   репро ДО написания тестов, не самими тестами. Исправлено —
   `.replace(/\\/g, '/')`.
2. `tsx` по умолчанию: 100% tsx-блоков во всех пакетах падали с "Cannot
   use JSX unless the '--jsx' flag" — Vue-пакеты не настраивают
   JSX/React-типы, блок часто иллюстративный React-псевдокод "если вы в
   React", который сам пакет никогда не смог бы скомпилировать. `tsx`
   убран из `DEFAULT_LANGS` (только `ts`), доступен через `--lang ts,tsx`.
3. Изоляция блока от блока: доминирующий класс шума — "Cannot find name
   X" (переменная объявлена в СОСЕДНЕМ блоке того же README). Попробовали
   накопление всех блоков файла в одну программу — это ПОМЕНЯЛО класс
   ложных срабатываний на худший: независимые альтернативные примеры,
   переиспользующие одно имя (`toast`, `useForm`), стали читаться как
   "Cannot redeclare block-scoped variable" — пугающий отчёт о
   несуществующем баге, хуже, чем очевидное "нет контекста". Откатили
   назад к изоляции, вместо этого точечно подавили заведомо ненадёжные
   коды диагностик, а не пытались угадать: `2304`/`2552` (Cannot find
   name), `6133` (declared but never read — обработчик, вызываемый не
   в этом фрагменте), `2307` с ОТНОСИТЕЛЬНЫМ путём (гипотетический файл
   в проекте читателя, `./App.vue`), `2792` (пакет не резолвит
   self-reference, потому что его СОБСТВЕННЫЙ tsconfig не включает
   `moduleResolution: bundler/node16/nodenext` — это ограничение
   окружения, а не баг в доках). `2307` для ГОЛОГО имени пакета
   (self-reference) остаётся находкой — это и есть исторически ценный
   случай.

**Реальные баги, найденные дого-дуингом (не гипотетические)**:

- `vue-state-machine`: 5 мест в README (строки 88, 89, 121, 146, 147) всё
  ещё импортируют нескопированное `vue-state-machine` вместо
  `@macrulez/vue-state-machine` — остаток исторического scope-бага,
  пропущенный при более раннем ручном исправлении этого же пакета.
- `responsive-media`: пример `useTemplateRef('card')` без явного дженерика
  возвращает `Readonly<ShallowRef<unknown>>`, что не проходит по
  `useContainerState`'s `Ref<Element | null>` — пример реально не
  скомпилировался бы и в настоящем строгом Vue-проекте читателя.
- `vue-network-dashboard`: пример `addMock({...})` не указывает
  обязательное поле `enabled` из `MockRule`.

Найдены, но НЕ исправлены в рамках этой задачи (задача — построить
инструмент, не пройтись по всем 17 пакетам) — пользователю решать,
чинить ли сейчас.

**Проверено на реальном коде**: прогнано на всех 21 пакетах в
`C:\work\NPM` — после всех фильтров осталось 3 пакета с реальными
находками (выше) и 2 с остаточным шумом низкой уверенности
(`vue-command-palette`/`vue-worker-kit` — "implicitly any" каскадом от
уже подавленной вышестоящей ошибки; задокументированное, обобщённо
неустранимое ограничение метода изоляции блоков, тот же класс, что
Nuxt-строковые-пути в `dead-exports` и subpath-импорты в `case-check`).

**Флаги**: `[dir]` (позиционный, по умолчанию `.`) — директория пакета;
`--file <path>` (повторяемый) — какой(-е) markdown-файл(ы) проверять,
относительно `[dir]` (по умолчанию `README.md`); `--lang <list>` —
языки фенс-блоков для проверки (по умолчанию `ts`); `--tsconfig <path>`
— переопределить автоопределяемый `tsconfig.json`; `--json`/`--quiet`/
